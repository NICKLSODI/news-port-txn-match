# News–Customer Matching · INVX

ระบบจริงตามสเปค STEP1–STEP8 (136 กฎ) — ข่าวใหม่จาก Cafe Invest เข้ามา 1 ชิ้น
ระบบบอกว่าควรติดต่อลูกค้าคนไหน เรียงตามคะแนน พร้อมเหตุผลที่อ้างเลขกฎได้ทุกแถว

- **news-centric** — เปิดข่าว 1 ชิ้นเห็นรายชื่อลูกค้า ไม่ใช่เปิดลูกค้าแล้วหาข่าว
- **ไม่มี sentiment** — ไม่บอกว่าข่าวดีหรือร้าย แสดงชื่อบทความจริงให้ RM อ่านเอง
- **ทำงานบนรหัสที่ปิดบังแล้ว 100%** — ไม่มีชื่อ เลขบัตร หรือเลขบัญชีในระบบ
- **ไม่มั่นใจ = ไม่จับคู่** แต่ต้องรายงานทุกครั้ง ห้ามเงียบ

## อัปเดตข้อมูลลูกค้าจากหน้าเว็บ

หน้า **อัปโหลดข้อมูล** (`/upload`) รับไฟล์ Excel สองไฟล์พร้อมกันเท่านั้น — ไฟล์เดียวไม่รับ

| ไฟล์ | คือ | คอลัมน์ที่บังคับ |
| --- | --- | --- |
| พอร์ต | STEP1 HOLDINGS | `customer_key` `account_key` `m_id` `product_code` `product_txt_key` `aum` `thb_unrealized_avg` `record_date` |
| รายการเทรด | STEP1 TRANSACTIONS | `customer_key` `account_key` `m_id` `product_code` `product_txt_key` `record_date` `txn_type` `confirm_unit` `trading_value` |

ต้อง mask มาก่อน — ลบ `cardid` `cust_name_th` `account` `marketing_name_th` แล้วแทนด้วยรหัส
(`customer_key` = CUST00001 · `account_key` = ACCT00001 · `m_id` หรือ `rm_id` = M001) ตารางแปลงกลับ
เก็บแยก ห้ามติดมาในไฟล์

วิธีทำจริงตามที่หน้าเว็บบอก: กดปุ่มโหลดคู่มือในหน้า `/upload` (เสิร์ฟจาก
`memie/วิธี mask ด้วย Copilot บนเว็บ.md` ผ่าน `GET /api/mask-guide`) → เปิด Copilot บน
microsoft365.com ด้วย account บริษัท → แนบสามไฟล์ (คู่มือ .md + Portfolio + TXN) → พิมพ์ `ทำตาม .md`
→ เอาไฟล์ `_MASKED` สองไฟล์กลับมาอัปโหลด

ข้อจำกัดที่ `backend/app/upload.py` บังคับจริง (ไม่ผ่าน = ไม่นำเข้า ข้อมูลเดิมไม่ถูกแตะ):

- `.xlsx` เท่านั้น อ่านชีตแรก ไฟล์ละไม่เกิน 80 MB
- ห้ามมีคอลัมน์ PII ที่ระบุไว้ และห้ามมีเลข 13 หลักหรืออีเมลหลงในช่องไหนก็ตาม
- `customer_key` / `account_key` / `m_id` ต้องเป็นค่าคงที่ ไม่ใช่สูตร และไม่มี `#N/A`
- ห้ามมีชีต `customer_map` / `account_map` / `rm_map` ติดมา
- `customer_key` ต้องมาจากตารางแปลงชุดเดียวกันทั้งสองไฟล์ ไม่ตรงกันเลย = ไม่ผ่าน (R1.3)
- `m_id` ต้องเป็นรหัส ถ้ายังเป็นชื่อคนไทย = ไม่ผ่าน (R1.9)
- วันที่ต้องเป็น `YYYY-MM-DD` มูลค่าเป็นสกุลบาทแล้ว (R1.8)
- แถวไม่มี `product_code` = ยอดเงินคงเหลือ ระบบข้าม (R1.6) · แถวไม่มี `customer_key` ข้ามทั้งแถว (R1.3)
- enum ที่ไม่รู้จักไม่ทำให้ไฟล์ตก แต่จัดเข้า `OTHER` และขึ้นหน้าตรวจสอบข้อมูล (R1.5)

ลำดับการทำงาน: ตรวจ (`POST /api/upload/check`) → ย้ายไฟล์ชุดเดิมไป `data/archive/<เวลา>/`
→ นำเข้าใหม่ทั้งชุด (R1.7 ไฟล์ล่าสุดคือความจริง) → จับคู่ใหม่ทุกบทความ ใช้เวลารวมราวครึ่งนาที
ต่อไฟล์ 12 MB / 156k แถว

## เมื่อมีข้อมูลใหม่ที่ไม่ตรงกับที่ตั้งไว้

ระบบไม่เดาเงียบ — ทุกอย่างที่อ่านไม่ออกเข้าตาราง `unmapped` แต่เดิม**ไม่มีอะไรส่งเสียง**
หมวดข่าวใหม่ที่ไม่รู้จักจึงหายไปได้เป็นเดือน (R3.16 ข้ามทั้งบทความ) ตอนนี้แก้สามชั้น

### ชั้น 1 — ระบบบอกเอง

`GET /api/health` คืน `alerts` ที่ขึ้นเป็นแถบเตือนบนหัวจอทุกหน้า กดซ่อนได้แต่ไม่หายถาวร

| ระดับ | เมื่อไหร่ | ทำไมถึงร้ายแรงระดับนั้น |
|---|---|---|
| สูง | หมวดข่าวใหม่ที่ไม่รู้จัก | ทิ้งทั้งหมวด ไม่ใช่แค่บางแถว — ไม่มีใครได้รับเลย |
| สูง/กลาง | ของที่อ่านไม่ออกซึ่งเพิ่งโผล่ใน 7 วัน | ระดับตามชนิดที่แย่ที่สุดที่พบ |
| กลาง | ข้อมูลลูกค้าเก่าเกิน 7 วัน | รายชื่ออาจไม่ตรงพอร์ตปัจจุบัน |

ป้าย "ใหม่" จะเงียบไว้ถ้าฐานข้อมูลเองยังอายุไม่ถึงกรอบเวลา — ตารางที่เพิ่งสร้าง
มี `first_seen` ใหม่หมดทุกแถว บอกว่า "พบ 280 รายการใหม่" ก็ทำให้เข้าใจผิดว่าเพิ่งเกิดปัญหา

### ชั้น 2 — เรียงตามผลกระทบ ไม่ใช่จำนวนครั้งที่เจอ

ที่ตรวจไม่ผ่าน **ถูกทิ้งและบันทึกลง `unmapped` bucket `ai`** — ห้ามเงียบ (STEP8)
ที่ถูกทิ้งจริงส่วนใหญ่คือหุ้นต่างประเทศที่ไม่มีลูกค้าถือ (CGN POWER, SPIC) ซึ่งถูกต้องแล้ว

**ทิศทางจาก AI ใช้เป็นสัญญาณชั้น 2** และเฉพาะเมื่อ **กฎสรุปไม่ได้** (`overall = unknown`)
ไม่ใช่เมื่อ "ไม่มีสัญญาณเลย" — เขียนเงื่อนไขผิดครั้งแรกแล้ว AI ไม่เคยถูกเรียกใช้จริงทั้งรอบ
เพราะเคสที่เป็นปัญหาคือมีสัญญาณจากถ้อยคำแต่ขัดกันเองจนตอบ unknown
หน้าจอแสดงที่มาว่า "AI อ่านเนื้อหาเต็มแล้วยกประโยคนี้มา" พร้อมประโยค — RM แยกออกว่าอันไหนมาจากไหน

**R3.3 ยังบังคับ**: แม่ของ Brief ห้ามมี entity รวม AI จึงอ่านที่ระดับข้อย่อย (`segment_text`)
ไม่ใช่เนื้อหาเต็มของแม่ (เผลอครั้งแรกแล้วแม่ Brief ได้ `AOT ERW CENTEL MINT` รวมกัน
ถอนออกด้วย `--clean-briefs`)

### หน้า "รายชื่อที่ต้องโทร" — เรียงด้วยเงิน ไม่ใช่คะแนน

ตอบสามคำถามของ RM ตอนเช้าในหน้าเดียว สลับได้สองมุม

| มุม | คำถาม | เรียงตาม |
|---|---|---|
| ตามลูกค้า (ค่าเริ่มต้น) | ควรโทรหาใครก่อน | เงินที่ข่าวแตะ · สลับเป็นคะแนนได้ |
| ตามข่าว | ข่าวชิ้นนี้ไปโดนใคร | เงินรวมที่ข่าวแตะ + ลูกค้ารายใหญ่ 5 คนต่อข่าว |
| ตามหุ้น | ข่าววันนี้ทำให้ตัวไหนต้องโทรคุย | เงินที่ลูกค้าของ RM ถือในตัวนั้น + รายใหญ่ 4 คนต่อตัว |

มุม "ตามหุ้น" ทำเป็นการ์ดไม่ใช่ตาราง เพราะหนึ่งหุ้นมีของที่ต้องอ่านพร้อมกันหลายชนิด
(เงิน · ทิศทาง · จำนวนคน/ถือจริง · ข่าวที่เป็นเหตุ · ชื่อลูกค้ารายใหญ่) ยัดลงตารางแล้ว
คอลัมน์เยอะจนต้องเลื่อนและสายตาต้องกระโดดไปมา — ต่างจากหน้า "หาจากหุ้น" ที่ดูทีละตัว
จากทั้งบริษัท อันนี้คือรายการตัวที่ข่าวแตะ เฉพาะในบุ๊กของ RM คนเดียว

ครั้งแรกเขียนแบบวนยิงคิวรีต่อหุ้น ใช้เวลา 8 วินาที ซึ่งช้าเกินกว่าจะเปิดทุกเช้า
แก้เป็นอ่าน (หุ้น, ลูกค้า) รอบเดียวแล้ววิเคราะห์บทความชิ้นละครั้ง เหลือ 0.28 วินาที

**"เงินที่ข่าวแตะ" = มูลค่าที่ลูกค้าถือในตัวที่ข่าวพูดถึง** (`matches.holding_value`)
ไม่ใช่มูลค่าพอร์ตทั้งใบ และไม่ใช่คะแนน — คะแนนบอกว่าข่าวเกี่ยวกับเขาแรงแค่ไหน
แต่ไม่บอกว่าคุยแล้วได้เท่าไร ลูกค้าคะแนน 61 ที่ถือของตัวนั้น 26.9 ลบ. คุ้มกว่าคะแนน 534 ที่ถือ 7.6 ลบ.

สองข้อที่ต้องรู้เวลาอ่านตัวเลขนี้:

- **รวมแบบไม่นับซ้ำต่อหุ้น** — ถ้าวันนั้นมีข่าวถึง NVDA สามชิ้น ลูกค้าที่ถือ NVDA ก้อนเดียว
  ต้องนับครั้งเดียว ไม่ใช่สามเท่า (SQL ยุบเป็นราย (ลูกค้า, หุ้น) ด้วย MAX ก่อนรวม)
  ตอนเขียนครั้งแรกรวมตรง ๆ แล้วเห็นยอดโผล่เกินมูลค่าพอร์ตทั้งใบ จึงจับได้
- **ยอดยังมากกว่ามูลค่าพอร์ตของบางคนได้** และไม่ใช่บั๊ก — `portfolio_value` เป็นภาพ
  ณ วัน snapshot (2026-06-30) ส่วนรายการที่ซื้อหลังวันนั้นถูกนับเป็นการถือครองด้วย (R1.17)
  หน้าจอจึงไม่แสดง "% ของพอร์ต" ในหน้านี้ ใช้แถบเทียบกับรายใหญ่สุดของวันแทน
  และเขียนกำกับไว้ใต้ตาราง

ระดับ L3/L5/L6 คิดมูลค่าจากสัดส่วนพอร์ตที่เกี่ยวข้อง (เช่น "ถือหุ้นกลุ่มธนาคาร 8% ของพอร์ต")
ไม่ใช่มูลค่าหุ้นตัวเดียว — เป็นไปตาม R6.3/R6.5/R6.6 และเขียนบอกในหน้าเช่นกัน

### สองมุมบนหน้า "หาจากหุ้น" — ภาพรวม และแยกตามผู้ดูแล

ระบบมีผู้ใช้สองประเภท และหน้านี้ต้องตอบทั้งคู่โดยไม่ต้องสลับหน้า

| ใคร | อยากรู้ | ได้จาก |
|---|---|---|
| คนในทีม (RM) | หุ้นตัวนี้ลูกค้าที่ฉันดูแลถือกี่คน มูลค่าเท่าไร | ตาราง "แยกตามผู้ดูแล" กดแถวเพื่อเจาะเหลือกลุ่มตัวเอง |
| คนนอกทีม (หัวหน้า/ส่วนกลาง) | ภาพรวมทั้งบริษัท | ทุกอย่างในหน้าโดยไม่ต้องเลือกอะไร — **เป็นค่าเริ่มต้น** |

- ระบบ **ไม่จำ** ว่าผู้ใช้เป็น RM คนไหน เพราะคนนอกทีมไม่มีคำตอบให้จำ
  ตัวกรองเป็นสถานะของหน้าจอ เปลี่ยนหุ้นแล้วรีเซ็ตกลับเป็นภาพรวมเสมอ
- ตัวกรองทำงานที่ SQL ไม่ใช่ที่หน้าเว็บ เพราะ `holders` มี `LIMIT` — ถ้ากรองทีหลัง
  ลูกค้าของ RM ที่ไม่ติดอันดับรวมจะหายไปเงียบ ๆ
- `holders_total` / `value_total` เป็นยอดทั้งบริษัทเสมอ แม้กำลังกรองอยู่ เพื่อให้เทียบสัดส่วนได้
- **เรียงตามมูลค่า ไม่ใช่จำนวนคน** — สองตัวนี้ชี้คนละคนจริง (PTT: RM003 ถือ 11 คนแต่ 7.7 ลบ.
  ขณะที่ RM002 ถือ 8 คนแต่ 19.9 ลบ.) ส่วน `% ของบุ๊ก` ยังสลับอันดับได้อีกชั้น
  (NVDA: RM002 3.2% > RM005 1.8% ทั้งที่ RM005 ถือมากกว่าเป็นตัวเงิน) จึงแสดงคู่กันทั้งสองค่า
- กำไร/ขาดทุนต่อผู้ดูแลบอกด้วยว่ามาจากกี่รายการ (`จาก 28/31 รายการ`) เพราะไฟล์พอร์ตส่ง
  `thb_unrealized_avg` มาไม่ครบทุกชนิดสินทรัพย์ (H-08 ไม่บังคับ) ถ้าไม่บอกจะดูเหมือนครบทั้งกลุ่ม
  และถ้าไม่มีเลยต้องขึ้น "ไม่มีข้อมูล" ไม่ใช่ 0

- **จุดเหนือแท่ง = วันที่มีข่าวถึงตัวนั้น** สีตามทิศทางที่ระบบอ่านได้ เลขบนจุดคือจำนวนข่าว
  คลิกที่แท่งเพื่อเปิดข่าววันนั้น
- **เส้นประ = ราคาเป้าหมายของ INVX Research** (มีแต่หุ้นไทยใน Coverage List) แกนราคาถูกขยาย
  ให้ครอบเส้นเป้าหมายเสมอ ไม่งั้นเส้นจะหลุดออกนอกกรอบ
- แถบล่าง = ปริมาณซื้อขาย
- เก็บ cache ในตาราง `price_cache` 30 นาที ถ้าดึงใหม่ไม่สำเร็จจะแสดงชุดเดิมพร้อมบอกว่าเป็นของเก่า

**ข้อควรรู้ทางเทคนิค**

- `frontend/public/tradingview.html` ต้องเป็นไฟล์จริงบนโดเมนเดียวกัน — widget ตรวจ origin
  ของหน้าที่ฝังมัน ถ้าใส่ HTML ใน `data:` URL จะค้างที่วงกลมโหลดไม่จบ
  ไฟล์นี้ตรวจรูปแบบ `symbol` ด้วย regex ก่อนใช้ และอยู่ใน iframe เพื่อกันสคริปต์ภายนอก
  แตะ DOM ของเว็บ — มันเห็นแค่ชื่อสัญลักษณ์ ข้อมูลลูกค้าไม่ได้ออกไปไหน
- `lightweight-charts` เป็นไลบรารีโอเพนซอร์สของ TradingView (Apache-2.0) คนละอย่างกับ widget
  ป้อนข้อมูลจากที่ไหนก็ได้ — ทำให้ JS bundle โตจาก 424 kB เป็น 605 kB (gzip 125 → 184 kB)
- endpoint ของ Yahoo เป็นของสาธารณะแต่ไม่ใช่ API ที่มีสัญญา ใช้กับเครื่องมือภายในได้
  แต่ห้ามเอาข้อมูลไปแจกจ่ายต่อ ถ้าขึ้นใช้งานจริงระดับบริษัทควรย้ายไป feed ที่มีสิทธิ์ใช้
  (SET / Refinitiv) — แก้ `prices.py` ไฟล์เดียว
